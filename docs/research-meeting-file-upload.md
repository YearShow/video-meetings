# Research: Технологии для загрузки файлов во встречу

**PRD:** [prd-meeting-file-upload.md](./prd-meeting-file-upload.md)
**План:** [plan-meeting-file-upload.md](./plan-meeting-file-upload.md)
**Дата:** 2026-10-14

Цель документа — выбрать, как технически реализовать загрузку, хранение и скачивание файлов до 500 МБ в существующей архитектуре (Nest.js 12 + CQRS + Prisma, Next.js 16 с Server Actions и JWT в httpOnly-cookie). Для каждого вопроса: варианты, рекомендация, риски. Утверждения, которые я не проверял на коде, помечены «проверить спайком».

## Сводка рекомендаций

| Вопрос                      | Рекомендация                                                                                                                                               |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Разбор multipart в `api`    | `busboy` напрямую (уже в зависимостях через multer), потоковая запись, без `FileInterceptor`                                                               |
| Путь web → api для загрузки | Браузер шлёт `XMLHttpRequest` напрямую в `api` с основным JWT (его отдаёт Server Action); в `api` включается CORS                                          |
| Путь для скачивания         | Короткоживущая подписанная ссылка: `api` выдаёт URL с токеном на 60 с, браузер открывает его навигацией                                                    |
| Запись на диск              | Временный файл в каталоге хранилища → `rename` → запись в БД; лимит считается по фактическим байтам                                                        |
| Абстракция хранилища        | Интерфейс `FileStorage` (save/read/delete/deletePrefix) с DI-токеном, ключи строит только сервер                                                           |
| Лимит 500 МБ                | Значение из конфига (`MAX_UPLOAD_BYTES`), в тестах — маленькое                                                                                             |
| Участники встречи           | Email остаётся как ввёл пользователь, сервер при создании встречи добавляет к нему `userId` (`{ email, userId }`); таблица `MeetingParticipant` (раздел 8) |
| Тесты `web`                 | Vitest + jsdom + Testing Library по гайду Next; загрузку оборачиваем в функцию с XHR, которую можно подменять                                              |

## Найденные расхождения плана с кодом

Их нужно закрыть до или в рамках фаз, иначе фазы не соберутся:

1. **Контракт `POST /meetings` и форма в `web` не меняются.** `web` отправляет участников как email (`apps/web/src/app/actions.ts`, `EMAIL_RE`), `CreateMeetingDto` по-прежнему валидирует `@IsEmail`. Сервер email не заменяет, а дополняет: при создании встречи находит пользователя по email и сохраняет рядом `userId` (раздел 8). Из-за этого меняется форма хранения `participants` (не `String[]`), а в `MeetingView` участник становится `{ email, userId }`. Сейчас `web` это поле не читает, так что интерфейс не затрагивается.
2. **В `web` нет страницы встречи.** Нет роутов вида `/meetings/[id]`, есть только `/`, `/auth/*`, `/register`. Фазы 4–5 говорят про «страницу встречи», её нужно создать.
3. **Участник не может открыть встречу.** `GetMeetingQuery` и `GetMeetingsQuery` ограничены `ownerId`. Чтобы участник видел встречу и раздел «Файлы», запросы надо расширить на участников (общий хелпер доступа из Фазы 1).
4. **`apps/api/CLAUDE.md` называет `participants` массивом email** — документацию нужно поправить вместе с Фазой 1.
5. **Каскад в БД не чистит диск.** `onDelete: Cascade` удалит строки файлов, но не сами файлы. Это уже учтено в плане командой очистки, но то же верно для каскада `User → Meeting` (удаление пользователя оставит файлы). Эндпоинта удаления пользователя нет, так что это риск на будущее.

## 1. Приём файла в `api`

### Варианты

- **A. `FileInterceptor` (multer) с `diskStorage`.** Стандартный путь Nest. Минусы: multer сам пишет файл по своим правилам (мимо нашей абстракции хранилища), интерцептор выполняется ДО обработчика, поэтому проверка доступа внутри CQRS-обработчика случится после получения всего файла; для кастомной записи нужен свой `StorageEngine`.
- **B. `FileInterceptor` с кастомным `StorageEngine`.** Решает связь с абстракцией, но API движка малоизвестный, а проблема порядка проверки доступа остаётся.
- **C. `busboy` напрямую в контроллере (рекомендуется).** Полный контроль: сначала guard и проверка доступа, затем разбор тела, поток файла уходит прямо в `FileStorage.save`. `busboy` 1.6 уже есть в `node_modules` как зависимость multer; в `apps/api/package.json` его нужно добавить явно (`npm i busboy @types/busboy -w apps/api`).
- **D. Сырой поток (`application/octet-stream`, имя в заголовке).** Меньше всего кода и нет накладных расходов multipart, `xhr.send(file)` работает напрямую. Минусы: имя и MIME приходится передавать в заголовках (кодирование не-ASCII), нетипичный контракт, парсер JSON в Nest может перехватить тело при `Content-Type: application/json`. Годится как запасной вариант.

### Рекомендация: C

Критичные настройки busboy:

- `limits: { files: 1, fileSize: MAX_UPLOAD_BYTES, fields: 0 или малое число, parts: 2 }`.
- **`defParamCharset: 'utf8'`.** По умолчанию busboy читает `filename` как `latin1` (подтверждено в `node_modules/busboy/README.md`), и кириллические имена превратятся в мусор.
- Событие `limit` у файлового потока означает, что файл усечён: прервать запись, удалить временный файл, ответить 413.
- Нет части `file` или больше одного файла → 400.

Порядок в Nest: `JwtAuthGuard` → guard доступа к встрече (читает `:meetingId`, обращается к тому же хелперу, что и запросы; 404 для посторонних, как уже делает `GET /meetings/:id`) → контроллер парсит multipart и отправляет `UploadMeetingFileCommand`. Команда принимает данные + поток (`Readable`), это не нарушает соглашение «только данные, без логики». Проверку доступа стоит продублировать в обработчике: guard нужен, чтобы не принимать тело от постороннего, обработчик — чтобы правило не обходилось другим входом.

Ранний отказ: если `Content-Length` > лимит + запас на multipart (например, 1 МБ), отвечать 413 до чтения тела. Нюанс: если сервер ответил и закрыл соединение, пока браузер ещё шлёт тело, XHR часто получает сетевую ошибку, а не 413. Поэтому основной UX — проверка размера в браузере (она уже есть в Фазе 5), серверный 413 — защита. UI при сетевой ошибке не должен утверждать «превышен лимит».

### Таймауты Node

`http.Server.requestTimeout` по умолчанию 300 000 мс (подтверждено в `@types/node`) и действует на получение ВСЕГО запроса, включая тело. 500 МБ на канале 10 Мбит/с — около 7 минут, такая загрузка будет оборвана. В `main.ts` нужно выставить `app.getHttpServer().requestTimeout = 0` (или десятки минут) и проверить, что `headersTimeout` не мешает. Добавить ручную проверку с ограничением скорости (Chrome DevTools throttling) в Фазу 3. Если появится reverse proxy, на нём тоже нужно снять лимиты (nginx: `client_max_body_size`, `proxy_request_buffering off`); сейчас такой инфраструктуры в репозитории нет.

## 2. Путь web → api

Ограничения `web` из `apps/web/CLAUDE.md`: запросы идут через Server Actions, CORS в `api` выключен, JWT лежит в httpOnly-cookie (JS его не видит).

### Варианты для загрузки

- **A. Server Action.** Не подходит: тело ограничено 1 МБ по умолчанию (`serverActions.bodySizeLimit`, подтверждено в docs Next), FormData парсится целиком, прогресса и отмены нет.
- **B. Route Handler в `web` как прокси на `api`.** Не нужен CORS, токен остаётся в cookie. Минусы: лишний хоп и двойной трафик через Node-процесс `web`, стриминг тела запроса в `fetch` требует `duplex: 'half'`, поведение на 500 МБ нужно проверить спайком. Если в `matcher` у `proxy.ts` попадёт этот роут, Next будет буферизовать тело (лимит `proxyClientMaxBodySize`, по умолчанию 10 МБ). Сейчас `matcher: '/'`, не менять.
- **C. Прямой запрос браузера в `api` (рекомендуется).** Нет лишнего хопа, `XMLHttpRequest.upload.onprogress` показывает реально отправленные байты, отмена через `xhr.abort()`. Тот же вид (клиент → хранилище напрямую) пригодится при переходе на S3. Плата — CORS и вопрос с токеном.

Прогресс и `fetch`: у Fetch API по-прежнему нет события прогресса отправки; потоковые тела запросов (`duplex: 'half'`) поддерживаются неравномерно между браузерами и меряют скорость подачи в поток, а не реальную отправку. Для прогресса использовать XHR ([источник](https://blog.openreplay.com/build-upload-progress-bar-js/), [обсуждение](https://github.com/whatwg/fetch/issues/577)).

### Токен для варианта C (решение: основной JWT)

Браузер не может прочитать httpOnly-cookie, поэтому токен нужно ему отдать. Выбрано: **Server Action читает cookie `accessToken` и возвращает JWT клиентскому коду**, который кладёт его в заголовок `Authorization` XHR-запроса. Отдельный тип токена и эндпоинт его выдачи не нужны.

Что это значит и что учесть:

- JWT (1 час, полный доступ) на время загрузки оказывается в памяти страницы, то есть защита httpOnly-cookie для него не действует: XSS на странице встречи может им воспользоваться. Минимизировать: держать токен только в локальной переменной на время запроса, не писать в `localStorage` и не логировать, соблюдать строгую политику контента страницы. Если требования к безопасности вырастут, переход на токен с узкими правами (`scope: 'upload'`, 2–5 минут) локален: меняются Server Action и guard эндпоинта загрузки.
- Срок токена проверяется один раз при получении заголовков, поэтому загрузка, начавшаяся до истечения, не оборвётся.
- Server Action должен вести себя как остальные запросы `web`: если cookie нет или `api` ответит 401, перенаправлять на `/auth/expired`.
- Эндпоинт загрузки защищён обычным `JwtAuthGuard`, как и остальные.

CORS в `api`: `app.enableCors({ origin: process.env.WEB_ORIGIN, methods: ['GET','POST'], allowedHeaders: ['Authorization','Content-Type'], maxAge: 600 })`. Не использовать `*`. Новая переменная `WEB_ORIGIN` (по умолчанию `http://localhost:3000`) попадает в `.env.example`. Нужно обновить строку в `apps/web/CLAUDE.md` «CORS в api не включён». Скачивание (навигация) CORS не требует, он нужен только загрузке.

### Скачивание (решение: подписанные ссылки)

`<a href>` не умеет передавать `Authorization`, а скачивание через `fetch` + Blob держит файл целиком в памяти (500 МБ). Выбрано: короткоживущая подписанная ссылка, которую браузер открывает обычной навигацией, поэтому нативный прогресс скачивания и менеджер загрузок работают, а `web` файл не проксирует.

Поток:

1. Клик по файлу вызывает Server Action, тот запрашивает у `api` `POST /meetings/:meetingId/files/:fileId/download-link` (под обычным `JwtAuthGuard`, с полной проверкой доступа к встрече). Ответ: `{ url }`.
2. `url` ведёт на `GET /meetings/:meetingId/files/:fileId/content?token=<jwt>`. Токен подписан тем же секретом, живёт 60 с и содержит `sub` (пользователь), `fileId` и `scope: 'download'`.
3. Клиент делает навигацию на `url` (скрытый `<a>` или `window.location`). Ответ с `Content-Disposition: attachment` оставляет пользователя на странице.
4. Эндпоинт проверяет токен, совпадение `fileId` и встречи из пути и **заново проверяет, что пользователь всё ещё владелец или участник**, затем стримит файл (раздел 5).

Важные детали:

- **`JwtAuthGuard` сейчас принимает любой JWT, подписанный секретом, и берёт `sub`.** Токен скачивания с `sub = id пользователя` прошёл бы как полноценный токен доступа ко всему API. Поэтому guard нужно изменить: отклонять токены с claim `scope` (или использовать `audience`), а эндпоинт скачивания, наоборот, принимает только токены с `scope: 'download'`. Это обязательное условие, в тесты Фазы 3 добавить кейс «токен скачивания не открывает `GET /meetings`».
- Токен в query-строке попадает в логи доступа и Referer. Смягчение: срок 60 с, ответ с `Referrer-Policy: no-referrer`, не логировать query-часть. «Одноразовость» потребовала бы хранения использованных токенов; для короткой ссылки с повторной проверкой доступа это избыточно, но если нужна, понадобится таблица или кэш с `jti`.
- Это не «публичная ссылка» из раздела «Не в скоупе»: она персональная, живёт минуту и привязана к проверке доступа при открытии.
- Менеджер загрузок может повторить запрос после истечения токена; тогда скачивание вернёт 401, и пользователь просто нажимает на файл ещё раз.
- Минус относительно прокси: запрос идёт на адрес `api` напрямую, значит адрес `api` должен быть доступен браузеру (то же требование уже есть у загрузки).

## 3. Запись на диск и атомарность

Порядок операций в `UploadMeetingFileHandler`:

1. Сгенерировать `fileId` (`crypto.randomUUID()`) на сервере; ключ хранилища `meetings/<meetingId>/<fileId>`. Имя от пользователя в ключ не попадает вообще.
2. `storage.save`: `pipeline(source, countingLimiter, createWriteStream(tmpPath, { flags: 'wx' }))` из `node:stream/promises`. Временные файлы лежат в `<root>/.tmp/` на том же томе, чтобы `rename` был атомарным.
3. После успешной записи: опционально `fsync`, затем `rename(tmp, finalPath)`.
4. Создать запись `MeetingFile` в БД. Если вставка упала — удалить итоговый файл.
5. При любой ошибке или обрыве (`premature close` у pipeline) — удалить временный файл.

Так «битых» записей в БД не бывает по построению: в худшем случае остаётся неучтённый файл на диске, невидимый пользователю.

Дополнительно:

- Размер считать по фактически записанным байтам (счётчик в Transform), а не по `Content-Length` и не по значению от клиента. Это вторая линия защиты помимо `limits.fileSize` в busboy.
- При запуске `api` чистить `.tmp` от файлов старше нескольких часов (остатки после падения процесса в момент загрузки).
- Обработать `ENOSPC` (диск заполнен) как 507/500 с очисткой, не оставляя частичный файл.
- Backpressure обеспечивает `pipeline`; читать файл целиком в память нельзя (отдельно проверить, что нигде не включён `memoryStorage`).

## 4. Абстракция хранилища

```ts
export interface FileStorage {
  save(
    key: string,
    source: Readable,
    opts: { maxBytes: number },
  ): Promise<{ size: number }>;
  read(key: string): Promise<Readable>;
  size(key: string): Promise<number>;
  delete(key: string): Promise<void>;
  deletePrefix(prefix: string): Promise<void>; // файлы встречи
}
export const FILE_STORAGE = Symbol('FILE_STORAGE');
```

- Реализация `LocalDiskStorage` берёт корень из `FILES_DIR` (`ConfigService`, обязательная переменная, пример в `.env.example`; в Docker — volume, не раздаётся статикой, то есть `ServeStaticModule` не подключать).
- Защита от path traversal: итоговый путь строится `path.resolve(root, key)` и проверяется, что он начинается с `root + path.sep`; ключи формирует только сервер из UUID. Unit-тест из Фазы 2 («имя с `../` не выходит за каталог») относится к проверке этого же метода.
- Замена на S3: `save` → `Upload` из `@aws-sdk/lib-storage` (принимает поток, делает multipart-загрузку), `read` → `GetObject`, `deletePrefix` → список + `DeleteObjects`. Контракт API не меняется. Для прямой загрузки браузера в S3 (pre-signed URL) схема из раздела 2 (вариант C с токеном) уже подготовлена.
- Раскладка `<root>/<meetingId>/<fileId>` даёт очистку встречи одним `rm -r`.

## 5. Скачивание на стороне `api`

- `GET /meetings/:meetingId/files/:fileId`: проверка доступа, запись должна принадлежать именно этой встрече (иначе 404; не искать файл только по `fileId`).
- Заголовки: `Content-Disposition: attachment; filename="<ascii-fallback>"; filename*=UTF-8''<percent-encoded>` (формат RFC 6266/5987; проще всего сформировать пакетом `content-disposition`, он уже зависимость Express), `Content-Type: application/octet-stream` (не доверять MIME от пользователя), `X-Content-Type-Options: nosniff`, `Content-Length` из БД (сверить с `stat`).
- Отдавать через `StreamableFile` с `createReadStream`; ошибка чтения или отсутствие файла на диске при наличии записи → 404/500 с логированием, а не падение процесса.
- Range-запросы (докачка) в PRD не требуются; `StreamableFile` их не поддерживает. Если понадобятся, придётся реализовать `206` вручную.

## 6. Модель данных (Prisma)

```prisma
enum MeetingFileStatus { UPLOADED }

model MeetingFile {
  id           String            @id @default(uuid(7))
  meetingId    String            @map("meeting_id")
  meeting      Meeting           @relation(fields: [meetingId], references: [id], onDelete: Cascade)
  uploadedById String            @map("uploaded_by_id")
  uploadedBy   User              @relation(fields: [uploadedById], references: [id], onDelete: Restrict)
  originalName String            @map("original_name")
  mimeType     String            @map("mime_type")
  sizeBytes    Int               @map("size_bytes")
  storageKey   String            @unique @map("storage_key")
  status       MeetingFileStatus @default(UPLOADED)
  createdAt    DateTime          @default(now()) @map("created_at")

  @@index([meetingId, createdAt])
  @@map("meeting_files")
}
```

- `sizeBytes` как `Int`: 500 МБ < 2 ГБ, а `BigInt` в Prisma возвращается как `bigint` и ломает JSON-сериализацию. Если лимит вырастет выше ~2 ГБ, потребуется миграция на `BigInt`.
- Статус: enum с единственным значением соответствует PRD («статусы обработки не вводим») и оставляет место для расширения. Допустимо вообще не хранить поле и в `FileView` отдавать константу; решение за владельцем PRD.
- `uploadedBy`: удаление пользователей пока не реализуется (решение), поэтому остаётся `Restrict`: он не даёт удалить пользователя с файлами. Когда такая операция появится, нужно будет выбрать между `Cascade` и `SetNull` (отображать «удалённый пользователь»).
- Имя файла: перед сохранением нормализовать (`path.basename`, убрать управляющие символы, обрезать до ~255 символов, NFC). Хранится только для отображения и заголовка скачивания.
- Модель чтения `file.view.ts`: `id`, `name`, `mimeType`, `size`, `createdAt`, `uploadedBy` (`{ id, email }`), без `storageKey`.

## 7. Лимит и тестируемость

- Вынести лимит в `MAX_UPLOAD_BYTES` (по умолчанию `524288000`, то есть 500 MiB; зафиксировать в документации, что «МБ» здесь — мебибайты, и согласовать формулировку в UI).
- e2e-тесты переопределяют лимит на 1 MiB, поэтому проверка 413 не требует отправки 500 МБ.
- Тест побайтового совпадения > 100 МБ: генерировать файл потоком из детерминированных или случайных чанков в `os.tmpdir()`, сравнивать sha256 потоково, не держать файл в памяти. Занимает секунды, но выделить в отдельный `describe` и не запускать в хуке (e2e в хук не входят).
- Тест обрыва: `supertest` плохо подходит для обрыва посреди тела, использовать `node:http` `request`, отправить часть данных и `req.destroy()`, затем с опросом убедиться, что `.tmp` пуст и записи в БД нет.
- Тест порядка проверок: посторонний пользователь получает 404 без чтения тела (можно проверить по тому, что файл не появился и ответ пришёл до завершения отправки).
- Тест хранилища: `mkdtemp` вместо реального каталога, очистка в `afterEach`.

## 8. Участники встречи (Фаза 1)

Принцип: клиент передаёт email, как и раньше. **Сервер не подменяет email на id, а добавляет к нему поле `userId`.** Форма и DTO не меняются, доступ к файлам проверяется по `userId`.

Обработчик `CreateMeetingHandler`:

1. Нормализовать email (trim + нижний регистр, как при регистрации) и убрать дубликаты.
2. Один запрос: `prisma.user.findMany({ where: { email: { in: emails } }, select: { id: true, email: true } })`.
3. Если нашлись не все, ответить `BadRequestException` со списком ненайденных email (контракт плана «несуществующий участник → 400» сохраняется). Приглашать email без аккаунта нельзя: для этого понадобилась бы сущность приглашения, это вне PRD.
4. Сохранить участников как пары `{ email, userId }`. Владельца в список не добавлять, его доступ проверяется по `ownerId`.

Хранение: `String[]` не вмещает пару, поэтому два варианта.

- **A. Таблица `MeetingParticipant` (решение подтверждено).** Поля `meetingId`, `email`, `userId` (FK на `users`, `onDelete: Cascade`), уникальность `(meetingId, userId)`, индекс по `userId`. Доступ: `meeting.findFirst({ where: { id, OR: [{ ownerId: userId }, { participants: { some: { userId } } }] } })`. Целостность на уровне БД, список встреч участника получается одним запросом. Колонка `Meeting.participants` удаляется миграцией.
- **B. Колонка `Json`** (отклонён) с массивом `{ email, userId }`. Миграция проще, но нет внешних ключей, а поиск по вложенному `userId` в Prisma неудобен и без индекса медленный. Выбирать, только если нужно минимизировать изменения схемы.

`email` в таблице дублирует `users.email` и нужен только для отображения «как приглашали»; если смена email пользователя когда-нибудь появится, его придётся обновлять или брать из `users` через связь.

Миграция существующих данных: в `meetings.participants` лежат email, их нужно превратить в строки `MeetingParticipant` с найденным `userId`. SQL-миграция: `INSERT INTO meeting_participants (meeting_id, email, user_id) SELECT m.id, u.email, u.id FROM meetings m JOIN LATERAL unnest(m.participants) AS p(email) ON true JOIN users u ON u.email = lower(p.email) ON CONFLICT DO NOTHING`, затем удаление старой колонки. Email без аккаунта не попадут никуда: перед применением сделать бэкап и перечислить потери запросом (`unnest` без `JOIN`). Миграция необратима по данным.

## 9. Фронтенд (`web`)

- **Загрузка:** функция `uploadFile({ url, token, file, onProgress, signal })` на `XMLHttpRequest`: `xhr.upload.onprogress`, `xhr.timeout = 0`, отмена через `AbortSignal` → `xhr.abort()`. Показать состояние «Завершаем…» после 100 %, пока сервер переименовывает файл и пишет в БД (событие `load` приходит позже). Сетевую ошибку не трактовать как 413 (см. раздел 1).
- **Drag-and-drop и выбор файла:** кандидаты — `DropZone` и `FileTrigger` из `react-aria-components` (на нём построен HeroUI v3, доступны с клавиатуры из коробки) либо `react-dropzone`. Наличие и экспорт этих компонентов в установленной версии HeroUI нужно проверить через скилл `heroui-react` до начала Фазы 5. Свой `input type=file` с `onDrop` допустим, но доступность придётся делать вручную.
- **Один файл за раз:** на `drop` брать `files[0]` и показывать сообщение, если их несколько; `input` без `multiple`.
- **Обновление списка:** после успеха вызвать Server Action с `revalidatePath` / `router.refresh()`.
- **Тесты (Фаза 4):** по гайду Next (`node_modules/next/dist/docs/01-app/02-guides/testing/vitest.md`): `vitest`, `@vitejs/plugin-react`, `jsdom`, `@testing-library/react`, `@testing-library/dom`, `vite-tsconfig-paths`; добавить скрипт `test` в `apps/web/package.json`, чтобы его подхватывал корневой `npm run test`. Гайд прямо предупреждает: Vitest не поддерживает `async` Server Components, значит списки с серверным получением данных тестируем через клиентские презентационные компоненты (данные приходят пропсами), а страницы целиком — e2e (Playwright MCP по `apps/web/CLAUDE.md`).
- В jsdom нет реальной отправки XHR: прогресс и отмену тестировать через подмену `XMLHttpRequest` (фейковый класс, вызывающий `upload.onprogress`). Библиотеки вроде MSW для событий прогресса отправки не рассматривал, проверить отдельно, если захочется отказаться от ручного фейка.
- Правила проверки UI из `apps/web/CLAUDE.md` (Playwright MCP, скилл `ui-ux-pro-max`, 375 px, тёмная тема) применимы к Фазам 4–5.

## 10. Что сознательно не берём

- **tus / resumable / chunked:** вне скоупа PRD. Для файлов 500 МБ на плохих сетях это самый заметный будущий апгрейд; выбранная абстракция хранилища не мешает добавить `tus-node-server` позже.
- **Uppy и аналогичные готовые загрузчики:** тяжёлые, свой стиль, дублируют HeroUI; для одного файла без возобновления избыточны.
- **Антивирус, превью, транскрипция:** вне скоупа.
- **Загрузка сразу в S3 по pre-signed URL:** вне итерации (только локальный диск), но архитектура не закрывает этот путь.

## Предлагаемые изменения плана

1. Фаза 1: при создании встречи находить пользователей по email и сохранять `{ email, userId }` (таблица `MeetingParticipant`, форма и DTO не меняются), мигрировать данные, расширить `GetMeeting(s)Query` на участников; политика для email без аккаунта: 400 со списком.
2. Фаза 2: добавить зависимость `busboy`, переменные `FILES_DIR`, `MAX_UPLOAD_BYTES`, `WEB_ORIGIN`, настройку `requestTimeout`, guard доступа до чтения тела, Server Action, отдающий JWT из cookie для XHR.
3. Фаза 3: добавить очистку `.tmp` при старте и ручную проверку на медленном канале; эндпоинт выдачи ссылки скачивания и скачивание по токену (`scope: 'download'`), изменение `JwtAuthGuard` (отклонять токены со `scope`) и тест на это.
4. Фаза 4: добавить создание страницы встречи `/meetings/[id]` и Server Action получения ссылки скачивания; тест фазы: клик запрашивает ссылку и инициирует навигацию на неё.
5. Фаза 5: XHR-обёртка загрузки, выбор компонента drop-зоны.
6. Спайк до начала реализации (около часа): загрузка 500 МБ напрямую в `api` с busboy, замер памяти процесса и поведение `requestTimeout` на медленном канале.

## Принятые решения

1. Токен загрузки: основной JWT, отдаваемый Server Action (раздел 2).
2. Скачивание: короткоживущие подписанные ссылки (раздел 2).
3. Участники: только пользователи с аккаунтом; email без аккаунта при создании встречи даёт 400, при миграции такие записи удаляются (бэкап и перечень потерь перед применением) (раздел 8).
4. Удаление пользователей (и, значит, поведение `uploadedBy`) в этой итерации не делаем.
5. `Meeting.participants` заменяется таблицей `MeetingParticipant` (раздел 8).
6. Лимит файла — 500 MiB (524 288 000 байт), «МБ» в PRD и интерфейсе читается как мебибайты (раздел 7).
